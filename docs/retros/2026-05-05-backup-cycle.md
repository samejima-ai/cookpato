## A. 汎用パターン提案（Dialog ハーネス取り込み推奨）

汎用性が高く、本サイクル以降のあらゆるプロジェクトで効果が見込めるもの。
取り込み優先度順に記載。

### A1. L0 対話：事故起点プローブ（最優先）

**取り込み先候補**：`layer0-spec-architect/references/dialog-questions.md`

**現状の問題**
本サイクルの初手で、ユーザー発話「ストックの保存方法について…ローカル保存して欲しい」に対して、AI は技術回答（「すでに永続化済み」）から入った。実際の動機は **2 ターン目で初めて出てきた**「妻のアプリで消えていた」という事故報告。
事故起点の要望は、技術的事実回答より **背景共有が優先されるべき**だった。背景を握ってからでないと正しい対策設計に進めない。

**提案差分**
`dialog-questions.md` に「事故起点プローブ」セクションを追加：

> ### 事故起点プローブ
>
> ユーザーが既存システムの機能変更・追加・確認を要求した際、初手で**1 問だけ**以下を投げる：
>
> > 「何かきっかけになる出来事がありました？」
> > 「最近うまくいかないことありました？」
>
> Yes 系の応答が返ってきた場合、技術的事実回答より**事故事実の聞き取り**を優先する。
> No 系応答なら通常の対話フローへ。
>
> 適用シーン：「保存方法について…」「○○の動作確認したい」「機能を追加したい」など、
> **既存システムへの言及を含む**初手発話。新規機能の純粋な構想要求では適用しない。

**根拠**
事故起点の要望に対して通常の機能対話フローを進めると、対策の設計（バックアップ）にたどり着くまで複数ターンを浪費する。1 問のプローブでショートカット可能。

**汎用性の根拠**
既存システム保守・運用フェーズ（Lifecycle ≥ 1）のあらゆるプロジェクトで適用可能。新規構築フェーズでは適用しないため副作用なし。

### A2. SPEC：機能間相互作用セクション（高優先）

**取り込み先候補**：`layer0-spec-architect/references/meta-spec-template.md`

**現状の問題**
本サイクルで Copilot レビューが捕捉した「インポート復元後に A 層スナップショットが古いまま残り、同日中の自動復元で巻き戻る」バグは、SPEC で **A 層と B 層を独立に**定義していたことが根本原因。
A 層の「日次スナップショット」と B 層の「インポート復元」が**永続化レイヤを共有している**事実を SPEC で明示していなかったため、L1 実装でも当該相互作用への対処が漏れた。

**提案差分**
`meta-spec-template.md` の SPEC.md テンプレに新セクションを追加：

> ### 機能間相互作用（永続化レイヤ・状態共有）
>
> 複数機能が同一の永続化レイヤ（DB / localStorage / ファイル等）または共有状態を読み書きする場合、
> 機能ごとの仕様だけでは整合性を保てない可能性がある。以下を明示する：
>
> - **共有レイヤ一覧**：機能 A・B・C がどのキー／テーブル／ストアを共有するか
> - **副作用マトリクス**：機能 X の実行が機能 Y の状態にどう影響するか
> - **同時刻整合性ルール**：例「インポート時は A 層スナップショットも当日付で強制更新」
>
> このセクションは**データ系機能・永続化機能・トランザクション系機能**で必須。
> ステートレスな表示系・計算系のみの機能では省略可。

**根拠**
本サイクルの Copilot 指摘は、L1 自己検証では捕捉できない種類のバグだった（時間軸を含むクロス機能シナリオ）。SPEC レベルで「相互作用」を文書化していれば、L1 が実装で自然に対処できた。

**汎用性の根拠**
データを扱う多くのプロジェクトに該当。仕様レビュー時のチェック観点としても流用可能。

### A3. REGIME：データ整合性事故履歴オーバーライド（中優先）

**取り込み先候補**：`layer0-spec-architect/references/regime-assessment.md` および `nfr-scoring.md`

**現状の問題**
本サイクルは M1 自己検証のみで進行。Copilot レビュー（≒疑似的な独立検証）が**実質的に層 1.5 として機能**し、データ整合性に関わる重要バグを救った。
M1 で同種の機能を進める場合、Copilot 等の自動レビューがない環境ではバグが本番（妻の端末）まで到達するリスクがある。

**提案差分**
`regime-assessment.md` のオーバーライド条件節に追加：

> #### オーバーライド：データ整合性事故履歴
>
> 過去 1 年以内に当該プロジェクトで**データ消失・破壊事故が報告されている領域**への変更は、
> R スコア +1 を加算する。結果として M2 以上が強制される場合がある。
>
> 「事故領域」の判定は履歴層（CHANGELOG / INTENT / 振り返り献上）からキーワード抽出する：
> - データ消失 / 消えた / 飛んだ
> - 破壊 / 壊れた / 不整合
>
> 適用例：
> - localStorage / IndexedDB の構造変更（実例：本サイクル）
> - DB マイグレーション
> - 既存データのスキーマ変更を伴う機能

**根拠**
データ消失・破壊系の事故は **再発時のユーザー体験への打撃が極めて大きい**（信頼喪失）。独立検証ありの M2 へ自動昇格させる費用対効果は高い。
本サイクルは M1 で進めて結果オーライだったが、Copilot レビューがなければバグは本番で発覚していた可能性がある。

**汎用性の根拠**
事故履歴は履歴層から機械的に抽出できる。オーバーライド条件として明確で、判定揺らぎが少ない。

### A4. L1 起動時：依存導入チェック（中優先）

**取り込み先候補**：`layer1-autonomous-dev/SKILL.md`（処理フローのステップ 1）

**現状の問題**
本サイクルの L1 で、最初の `npm run typecheck` が `node_modules` 未配置による型定義不在エラーで失敗。`npm ci` を先に走らせれば回避できた。
新規環境・worktree・キャッシュ吹き飛び等で再現する典型的な摩擦。

**提案差分**
`layer1-autonomous-dev/SKILL.md` のステップ 1（ドキュメント受領）の直後に追記：

> #### 1.1 依存導入の事前チェック
>
> 計算センサー初回実行前に、依存関係が解決されているかを確認する：
>
> - Node プロジェクト：`ls node_modules/.package-lock.json` の存在確認 → なければ `npm ci`
> - Python プロジェクト：venv 確認 → なければ `pip install -r requirements.txt` または `uv sync`
>
> このチェックを省略するとセンサーが偽の失敗を返し、自力修正サイクルを浪費する。
> 「依存未解決」は仕様問題でも実装問題でもない、純粋な前提条件問題として扱う。

**根拠**
本サイクルで実際に発生した摩擦。ハーネスの想定する「クリーン環境」と現実の差を吸収するレイヤとして必要。

**汎用性の根拠**
あらゆる L1 起動で適用可能。コストはほぼゼロ（数秒の存在確認）、効果は確実。

### A5. センサー：UI 規約の grep ベース簡易チェック（低優先）

**取り込み先候補**：`layer0-spec-architect/references/dev-env-spec.md`（センサー定義のパターン例）

**現状の問題**
本サイクルで `RestoreToast` の閉じるボタンを `w-9 h-9`（36×36px）で実装。CLAUDE.md の UI 規約（タッチターゲット最小 44×44px、例外はストック行 `[−][qty][＋]` のみ）に違反していたが、`lint`/`test` では検出できず Copilot レビューで救われた。

**提案差分**
`dev-env-spec.md` に「規約 grep センサー」のパターン例を追加：

> #### パターン：プロジェクト固有規約の grep ベースセンサー
>
> CLAUDE.md / SPEC.md に定量的な規約（例：「最小サイズ N×N px」「禁止クラス X」）がある場合、
> grep ベースの簡易センサーで自動検出できる。コストが極小で、推論センサーの取りこぼしを補う。
>
> 例（Tailwind プロジェクトでのタッチターゲット 44px 規約）：
>
> ```bash
> # NG パターン: w-1〜w-10 / h-1〜h-10 が連続している箇所（44px 未満候補）
> # 許容例外はホワイトリストファイルで除外
> rg --type tsx 'w-(?:[1-9]|10) h-(?:[1-9]|10)' src/components \
>   | grep -v -f .lint-touch-target-allowlist
> ```
>
> センサーへの組み込み方：
> - 計算的センサーに `npm run lint:rules` 等として追加
> - 1 秒以内に完了する制約を守る
> - 違反検出時はファイル名と該当行を出力

**根拠**
本サイクルの違反は完全に防げた種類のミス。grep 1 行で検出可能。CLAUDE.md の規約を「文書」のままにせず実行可能化することで、L1 自己検証で確実に拾える。

**汎用性の根拠**
プロジェクト固有規約の文書化は M2 以上で標準。それを実行可能化するパターン例はあらゆるプロジェクトで応用できる。具体的な grep 式は CLAUDE.md の規約からほぼ機械的に導出可能。

## B. プロジェクト固有の学び（参考メモ）

### B1. iOS Safari 制約の早期可視化が交渉を成立させた

ユーザーから「同一ファイルを毎日自動上書き」「完全自動でやって」「1 タップにできない？」と段階的に要望が来た。AI 側は iOS Safari の File System Access API 非対応・自動ダウンロード非対応・OS 確認ダイアログ強制を**早期に表で提示**したことで、5 ターン以内に「週 1 タップ + 蓄積保存」の現実解に着地できた。
**学び**：技術制約を「できない」と一文で済ませず、「何ができないか・なぜか・代替は何か」を 3 軸の表で提示すると交渉が早い。

### B2. M1 で本機能を進めた結果

データ整合性クリティカルな機能を M1 自己検証のみで進めたところ、Copilot レビューが層 1.5 として機能して 2 件のバグを救った。
**学び**：本ケースは結果オーライだが、Copilot 等の自動レビューがない環境では危険。A3 のオーバーライド提案の根拠ケースとして記録。

### B3. ISO 週番号ファイル名の運用観察ポイント

`cookpato-backup-2026-W18.json` の ISO 週番号は厳密だが、妻の体感での直感性は未確認。日付（`2026-05-05.json`）の方が並びは自然な可能性。
**次回 L0 観察項目**：実機で 1〜2 ヶ月運用後に妻に聞く。

### B4. ストック行改修と消失タイミングの因果関係は未確定

ストック行改修の PR #18（StockItem スキーマは変更なし）と消失の因果は不明確。iOS Safari の auto-clear・ユーザー操作・PWA 更新時の SW 競合のいずれかが有力候補。再現条件不明のため**発生事実を前提とした防御**（バックアップ層）でカバーする方針を取った。
**学び**：原因不明でも防御は設計可能。原因特定に時間を浪費せず、防御層で実害を吸収する判断は妥当。

## C. サイクル全体所感

### うまくいった点

1. **L0 → L1 の引き継ぎ品質が高かった**：SPEC.md「バックアップ（二層構成）」が機能×条件粒度で完全確定していたため、L1 実装中の問い合わせゼロ
2. **計算センサーの効力**：lint で `useSemanticElements` 違反、test で不正日付 NaN 問題、typecheck で State 型不整合と、いずれも自動検出 → 自力修正で完結
3. **段階的な要件交渉**：3 軸表（実装/ランタイム/操作負担）で論点分解 → ユーザーが判断材料を持てた

### 改善点

1. **初動でユーザーの本音を引き出せなかった**（→ A1）
2. **クロス機能の整合性が SPEC で不足**（→ A2）
3. **データ整合性クリティカル機能を M1 で進めるリスク**（→ A3）
4. **L1 起動時の前提条件チェック不足**（→ A4）
5. **UI 規約準拠の自動チェック弱い**（→ A5）

### 次サイクルへ

A1〜A5 のうち少なくとも A1・A2・A4 は次サイクル前に取り込み済みにしておくと、同種の摩擦を構造的に防げる。A3・A5 は中長期で検討。
B 節は本プロジェクトのみの観察記録として保持。
