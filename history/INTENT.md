# 意図ログ

本ファイルは Cookパト の現役機能の「なぜこの条件で存在するのか」を記録する。
SPEC.md が「WHAT」を、本ファイルが「WHY＋却下案」を担う役割分担とする。
初期化サイクル（2026-05-12）では SPEC.md と過去 PR を一次情報源として最小エントリで開始し、
次サイクル以降の機能追加・変更で漸次エントリを増やす。

## 哲学: 早い・簡単・便利（2026-05-17 確立）

- **追加日**: 2026-05-17（妻の発話「Cookパトの哲学を設定する。早い、簡単、便利」）
- **意図**: Cookパトの全判断（機能追加・UX 変更・実装方針）に共通の判定指標を与え、機能過多化を未然に防ぐ。妻が既存献立アプリを離れた最大の理由「機能過多による操作負担」への構造的歯止め
- **意味**:
  - **早い** — 即時保存／最短手数／待ち時間ゼロ／無駄な確認なし
  - **簡単** — 学習不要／判断を強要しない／迷わない／タップだけで完結
  - **便利** — メモ帳より便利な明確な理由（日付自動生成・履歴検索・ストック永続）が機能する
- **判定ルール**:
  - 「3 語すべてに寄与する」または「1 語に大きく寄与し他 2 語を損ねない」場合のみ採用
  - 1 語でも損ねる変更は DONT.md に追記して却下
  - 3 語の競合時は **「簡単」を優先**（妻のメンタル負荷ゼロを最上位）
- **配置**: INDEX.md「哲学（判定指標）」セクション + CLAUDE.md「哲学（判定指標）」セクション
- **却下案**:
  - 単独 PHILOSOPHY.md 新規ファイル：3 語のみのコンパクトな指標で、独立ファイル化のメンテコスト > 一次参照経路の冗長性
  - CLAUDE.md のみへの記載：SPEC 判断時に INDEX.md 側から見えにくく、目的（WHY）としての位置づけが弱くなる
- **関連**: 全機能（既存・将来追加とも本指標で再評価可能）
- **確度**: 確定

## 機能ID: F001 - カレンダー無限スクロール

- **状態**: 現役
- **追加日**: 初回献上時（2026 年 4 月、PR #1 系列）
- **意図**: メモ帳の「日付・曜日フォーマットを毎月手作業で作る」不満を解消するため、画面遷移なしで連続閲覧できるカレンダーを単一画面に提供する
- **条件根拠**:
  - 月切替ボタンを置かない → 「ボタンが増えるとメモ帳の手軽さが損なわれる」原則
  - 当日が中央付近に来る自動スクロール → 起動直後の操作コストをゼロにする
  - 遠方の日の描画は遅延可だがデータは即保持 → 軽快感と整合性の両立
- **却下案**:
  - 月ビュー固定（カレンダー UI 標準）: 月切替操作が増え DONT.md「画面遷移なし」「登録ボタン排除」原則に反する
  - 仮想スクロール（react-window 等）導入: 依存追加のコスト > 得られる軽さ。手書きの IntersectionObserver で十分
- **関連**: F002, F009, F010
- **確度**: 確定

## 機能ID: F011 - フロート入力フォーム（FloatingEditor）

- **状態**: 現役
- **追加日**: 2026-05-13（妻の発話「料理リスト・ミニメモの入力時に画面上部にフロート入力フォーム。リストを邪魔せず、入力しながらリストを見て考えたい」）
- **意図**: 料理行・ちょいメモの編集経路を画面上部のフロートに集約し、編集中もリスト全体が見渡せる体験を提供する。旧モデル（textarea 全行一括編集 + 行内メモ input）はリストエリアに input を抱え込んでおり、編集中はリストが押し下げられ「リストを見ながら考える」体験を阻害していた
- **条件根拠**:
  - `position: sticky` で画面上部に固定 → 編集中もカレンダーの全体像が見渡せる
  - `EditingTarget` null 時は完全非表示 → DONT.md「使わない機能を画面に置かない」原則
  - uncontrolled + `key={target}` 再マウント → F002 既存の iOS Safari × IME 対策パターンを踏襲
  - blur / Enter で確定、Escape でキャンセル → ユーザーの意図が明確な経路に限定
  - 外タップでの確定／キャンセルは不採用 → 誤タップ時の意図不明確（妻が他の行をタップしようとした時に意図せず確定される事故）を避ける
  - 編集中対象に薄い背景色ハイライト → 「どれを編集中か」を妻が見失わない
- **却下案**:
  - 行単位 input をリスト内に並べる（フロートを使わない） → リスト下部に input が積み上がり、編集中の行が画面外に押し出される。妻の「リストを見ながら考える」体験を阻害
  - フロート内に複数行 textarea を持つ → 「全行一括編集モデルへの逆戻り」、行単位編集の利点（１行ずつ確定→次の行を見て考える）が失われる
  - フロート位置を画面下部にする（iOS の連絡先風） → virtual keyboard 起動時にフロートがキーボード上に乗ってリストを完全に覆う。上部 sticky なら keyboard との重なりを最小化できる
  - 検索候補・履歴を同フロートに同居 → 1 機能 1 責務原則、フロート自体が複雑化して妻のメンタル負荷増
- **関連**: F002, F003, F004（編集導線の主経路）
- **確度**: 確定

## 機能ID: F012 - 日付ごとスワップ

- **状態**: 現役
- **追加日**: 2026-05-17（妻の発話「献立の日を替えて丸ごと日にちを移動したり」）
- **意図**: 計画変更時に「火曜の予定を水曜に回したい」を最短手数で実現する。データ消失リスクをゼロにするため一方向移動ではなくスワップ（双方向入れ替え）を採用
- **条件根拠**:
