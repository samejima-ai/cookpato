# 意図ログ

本ファイルは Cookパト の現役機能の「なぜこの条件で存在するのか」を記録する。
SPEC.md が「WHAT」を、本ファイルが「WHY＋却下案」を担う役割分担とする。
初期化サイクル（2026-05-12）では SPEC.md と過去 PR を一次情報源として最小エントリで開始し、
次サイクル以降の機能追加・変更で漸次エントリを増やす。

## 哲学: 早い・簡単・便利（2026-05-17 確立）

- **追加日**: 2026-05-17（妻の発話「Cookパトの哲学を設定する。早い、簡単、便利」）
- **意図**: Cookパトの全判断（機能追加・UX 変更・実装方針）に共通の判定指標を与え、機能過多化を未然に防ぐ。妻が既存献立アプリを離れた最大の理由「機能過多による操作負担」への構造的歯止め
- **意味**:
  - **早い** — 即時保存／最短手数／待ち時間ゼロ／無駄な確認なし
  - **簡単** — 学習不要／判断を強要しない／迷わない／タップだけで完結
  - **便利** — メモ帳より便利な明確な理由（日付自動生成・履歴検索・ストック永続）が機能する
- **判定ルール**:
  - 「3 語すべてに寄与する」または「1 語に大きく寄与し他 2 語を損ねない」場合のみ採用
  - 1 語でも損ねる変更は DONT.md に追記して却下
  - 3 語の競合時は **「簡単」を優先**（妻のメンタル負荷ゼロを最上位）
- **配置**: INDEX.md「哲学（判定指標）」セクション + CLAUDE.md「哲学（判定指標）」セクション
- **却下案**:
  - 単独 PHILOSOPHY.md 新規ファイル：3 語のみのコンパクトな指標で、独立ファイル化のメンテコスト > 一次参照経路の冗長性
  - CLAUDE.md のみへの記載：SPEC 判断時に INDEX.md 側から見えにくく、目的（WHY）としての位置づけが弱くなる
- **関連**: 全機能（既存・将来追加とも本指標で再評価可能）
- **確度**: 確定

## 機能ID: F001 - カレンダー無限スクロール

- **状態**: 現役
- **追加日**: 初回献上時（2026 年 4 月、PR #1 系列）
- **意図**: メモ帳の「日付・曜日フォーマットを毎月手作業で作る」不満を解消するため、画面遷移なしで連続閲覧できるカレンダーを単一画面に提供する
- **条件根拠**:
  - 月切替ボタンを置かない → 「ボタンが増えるとメモ帳の手軽さが損なわれる」原則
  - 当日が中央付近に来る自動スクロール → 起動直後の操作コストをゼロにする
  - 遠方の日の描画は遅延可だがデータは即保持 → 軽快感と整合性の両立
- **却下案**:
  - 月ビュー固定（カレンダー UI 標準）: 月切替操作が増え DONT.md「画面遷移なし」「登録ボタン排除」原則に反する
  - 仮想スクロール（react-window 等）導入: 依存追加のコスト > 得られる軽さ。手書きの IntersectionObserver で十分
- **関連**: F002, F009, F010
- **確度**: 確定

## 機能ID: F002 - フリー入力（料理行＋ちょいメモ）

  - 主菜／副菜カテゴリ欄分離: DONT.md「カテゴリ分け排除」に反する

- **確度**: 確定

## 機能ID: F007 - バックアップ二層（A: localStorage 二重化 / B: 週1ファイル書き出し）

- **状態**: 現役
- **追加日**: 拡張サイクル（過去にストック消失の実例あり）
- **意図**: iOS の自動ストレージ削除・アプリ内バグでのデータ消失からデータを守る。失うとユーザー体験を著しく損なうストック・累積メダル等を保護
- **条件根拠**:
  - A 層: 起動時 1 日 1 回スナップショット、実質空検出で自動復元 → 無音・完全自動で妻の認知負荷ゼロ
  - B 層: 週 1 バナー + `<a download>` 方式 → iOS Safari の File System Access API 非対応制約下で最小タップ数
  - クリック発火 = 成功とみなす → OS ダイアログのキャンセル検知不可、UX シンプル優先
  - 蓄積型（同一ファイル上書きしない） → 月またぎ復元要求に対応、年 52 ファイル × 数 KB で容量問題なし
- **却下案**:
  - クラウド同期: DONT.md「完全ローカル原則」に反する。過去事故契機でも除外維持
  - 自動ファイル書き出し: iOS Safari ユーザージェスチャ必須制約により不可
  - IndexedDB 採用: 単一ユーザー・小データ量で localStorage の単純さが勝る
- **関連**: 全機能（データ永続化の基盤）
- **確度**: 確定

## 機能ID: F011 - フロート入力フォーム（FloatingEditor）

- **状態**: 現役
- **追加日**: 2026-05-13（妻の発話「料理リスト・ミニメモの入力時に画面上部にフロート入力フォーム。リストを邪魔せず、入力しながらリストを見て考えたい」）
- **意図**: 料理行・ちょいメモの編集経路を画面上部のフロートに集約し、編集中もリスト全体が見渡せる体験を提供する。旧モデル（textarea 全行一括編集 + 行内メモ input）はリストエリアに input を抱え込んでおり、編集中はリストが押し下げられ「リストを見ながら考える」体験を阻害していた
- **条件根拠**:
  - `position: sticky` で画面上部に固定 → 編集中もカレンダーの全体像が見渡せる
  - `EditingTarget` null 時は完全非表示 → DONT.md「使わない機能を画面に置かない」原則
  - uncontrolled + `key={target}` 再マウント → F002 既存の iOS Safari × IME 対策パターンを踏襲
  - blur / Enter で確定、Escape でキャンセル → ユーザーの意図が明確な経路に限定
  - 外タップでの確定／キャンセルは不採用 → 誤タップ時の意図不明確（妻が他の行をタップしようとした時に意図せず確定される事故）を避ける
  - 編集中対象に薄い背景色ハイライト → 「どれを編集中か」を妻が見失わない
- **却下案**:
  - 行単位 input をリスト内に並べる（フロートを使わない） → リスト下部に input が積み上がり、編集中の行が画面外に押し出される。妻の「リストを見ながら考える」体験を阻害
  - フロート内に複数行 textarea を持つ → 「全行一括編集モデルへの逆戻り」、行単位編集の利点（１行ずつ確定→次の行を見て考える）が失われる
  - フロート位置を画面下部にする（iOS の連絡先風） → virtual keyboard 起動時にフロートがキーボード上に乗ってリストを完全に覆う。上部 sticky なら keyboard との重なりを最小化できる
  - 検索候補・履歴を同フロートに同居 → 1 機能 1 責務原則、フロート自体が複雑化して妻のメンタル負荷増
- **関連**: F002, F003, F004（編集導線の主経路）
- **確度**: 確定

## 機能ID: F012 - 日付ごとスワップ

- **状態**: 現役
- **追加日**: 2026-05-17（妻の発話「献立の日を替えて丸ごと日にちを移動したり」）
- **意図**: 計画変更時に「火曜の予定を水曜に回したい」を最短手数で実現する。データ消失リスクをゼロにするため一方向移動ではなくスワップ（双方向入れ替え）を採用
- **条件根拠**:
  - **スワップ方式**: 一方向「移動（上書き）」は確認ダイアログが必須となり手数増、加えて誤操作で予定が消える事故を生む。スワップなら確認不要・常に可逆 → 哲学「早い」「簡単」両立
  - **日付ラベル長押し → 目的日タップ（2 タップ）**: 既存の料理行長押し（F004）と同型のジェスチャ語彙で学習負荷ゼロ
  - **視覚強調 `bg-blue-50 + ring-2 ring-blue-300`**: 今日（`bg-yellow-50`）と区別、移動中であることを色のみで伝える（説明テキスト不要 → 「簡単」）
  - **対象範囲 = `lines` + `memo`（done / cart 含む）**: 「この日の計画一式」のメンタルモデル。お気に入りは正規化キー集合のため自動追従、completedWeeks は別途再評価
  - **週達成は union のみ（減らない）**: F009「献血カウント」セマンティクス維持。スワップで未達成化する週があっても累積カウントは保護
  - **新規達成週のスプラッシュ発火**: F009 既存の「未達成 → 達成」トリガと同型扱い
  - **過去日 ↔ 未来日許可**: 「先週分の整理」「来週分の前倒し」両方の運用に対応
- **却下案**:
  - 「移動（上書き）」モード: 確認ダイアログ 1 枚増・データ消失リスクあり、スワップ比でメリットなし。DONT.md 哲学却下表に記録
  - 「空日にのみ移動可」: 既存予定への対応ができず用途が狭まる。スワップなら全ケース成立
  - ドラッグ&ドロップ: iOS Safari の長押しスクロールと干渉、長距離ドロップの誤爆、実装コスト > 2 タップ方式の手数差
  - 長押し → ポップオーバーメニュー（「日ごと移動」選択）: タップ 1 回増、新規 UI パターン追加。`簡単` を損ねる
  - 移動モード中の説明テキスト: 視覚強調で意図は伝わる、文言追加は読解負荷増。DONT.md 哲学却下表に記録
  - 複数日まとめ移動・週ごと移動: 用途希薄、手数増、`簡単` を大きく損ねる
  - アンドゥ機能: スワップは可逆操作なので「もう一度同じ操作」で戻る。アンドゥ UI 追加はメンタル負荷増
- **関連**: F002（lines/memo 編集）, F004（長押しジェスチャ語彙の共有）, F009（週達成評価）, F011（同時実行制約）
- **確度**: 確定

## 機能ID: F013 - 行間挿入（長押しメニュー化）

- **状態**: 現役
- **追加日**: 2026-05-17（妻の発話「献立行の間に追加の料理を入れたりできると良い」）
- **意図**: 末尾追加に加えて任意位置への挿入を可能にする。新規常設ボタンを増やさないという制約下で、既存の長押し（wobble）モードを「メニュー化」して統合
- **条件根拠**:
  - **wobble 中の行内 UI を `[✓][text][↑+][↓+][✕]` に置換**: 行幅 375px（iPhone 11）を維持するため `🛒`/`♡` を wobble 中のみ非表示。「長押し中は管理操作」「通常時は使用中操作」とモードを明確に分ける
  - **`↑+` / `↓+` は 44×44px**: iOS HIG 準拠、🛒/♡ と同サイズで継承
  - **挿入後即フロート編集起動**: 「挿入 → 入力」が 1 アクションで完結（哲学「早い」）
  - **空行（EmptyLineItem）への長押し無効**: 空行に対して削除・上下挿入はいずれも無意味。タップで編集開始の単機能に絞る
  - **キャンセル後の空行は残る**: F002「空行も保持可能」原則と整合。自動削除は予測不能挙動を生む
  - **既存行の reorder は引き続き禁止**: 「挿入は位置指定の追加」「reorder は既存データの移動」と境界を明示。reorder は判断を求めるため `簡単` を損ねる
- **却下案**:
  - ポップオーバーメニュー（テキストラベル選択 UI）: iOS コンテキストメニューと混同、新規 UI パターン追加。DONT.md 哲学却下表に記録
  - 行と行の隙間タップで一時的に「＋」表示: ヒット領域が小さく iPhone 11 で誤爆リスク高、新規ジェスチャ追加コスト
  - 既存末尾「＋追加」を「位置選択モード」に変更: タップ数増、`早い` を損ねる
  - wobble 中も `🛒` / `♡` を残す: 行幅 375px で破綻、誤爆リスク増
  - 「上に追加」のみで「下に追加」を省略（上の行への↓+で代用）: 末尾行の挿入が不可能化、メンタルモデルが歪む
- **関連**: F002（行追加の基本動作）, F003（並び替え禁止との境界）, F004（長押しジェスチャ・wobble モードの統合）, F010（空行 ★ プレースホルダ）, F011（挿入後の編集経路）
- **確度**: 確定
